# Отправители: как добавить почту и что при этом происходит

Письма уходят не с одного зашитого адреса, а из пула `smtp_accounts`. Пул сам
выбирает, с какого аккаунта отправить, сам держит дневные лимиты и сам
прогревает новые почты. Этот документ — про то, как добавить в него адрес.

Зачем пул вообще нужен: 250 писем в сутки с одного непрогретого Gmail — прямой
путь в спам за неделю, вместе с доменом. Прогрев не ускоряется добавлением
аккаунтов, но объём делится между ними, и каждый остаётся в своих пределах.

---

## Добавить отправителя

Два шага, оба обязательны. Строка без секрета не заработает, секрет без строки
не будет прочитан.

### 1. Секрет с логином и паролем

Имена собираются из `credentials_ref` по правилу `<REF>_USER` и `<REF>_PASS`.
Для `SMTP_ACC_2` это `SMTP_ACC_2_USER` и `SMTP_ACC_2_PASS`.

```bash
supabase secrets set SMTP_ACC_2_USER='partner.mail@gmail.com'
supabase secrets set SMTP_ACC_2_PASS='<пароль приложения Gmail>'
```

Для Gmail нужен именно **пароль приложения**, не пароль от аккаунта: обычный
пароль Gmail отвергает с ошибкой `534 Application-specific password required`,
и выглядит это как «письма молча не уходят».

Пароль в таблицу **не кладётся никогда**. В `credentials_ref` лежит только имя
секрета. Причина простая: у `anon` есть права на `smtp_accounts` ещё с миграции
038, то есть пароль в таблице читался бы публичным ключом из `index.html`.

### 2. Строка в пуле

```sql
INSERT INTO public.smtp_accounts
  (brand_id, email, provider, credentials_ref, status, ramp_stage, daily_limit, ramp_started_at)
SELECT id, 'partner.mail@gmail.com', 'gmail', 'SMTP_ACC_2', 'warming', 1, 10, now()
  FROM public.brands WHERE slug = '1xbet';
```

`ramp_started_at = now()` — не формальность: от неё считается вся лестница
прогрева. Поставить прошедшую дату значит выдать новому адресу лимит, который
он не заработал.

**`brand_id` обязателен, и подставлять чужой нельзя.** Отправитель принадлежит
одному бренду. Письмо LuckyPari, ушедшее с адреса 1xBet, вскрывает связку
брендов на стороне получателя — это правило проекта, а не оптимизация, и
функция выбора аккаунта фолбэка на «любой свободный» не имеет.

## Что происходит дальше само

### Прогрев

`fn_ramp_smtp_accounts` двигает лимит по календарю от `ramp_started_at`:

| Дни | Лимит в сутки | Стадия |
|---|---|---|
| 1–3 | 10 | 1 |
| 4–7 | 25 | 2 |
| 8–14 | 50 | 3 |
| 15–21 | 100 | 4 |
| 22–30 | 150 | 5 |
| 30+ | 250 | `status` → `active` |

Считается по возрасту аккаунта, а не по числу вызовов функции. Разница
существенная: при счёте вызовов пропущенный день сдвинул бы весь график, а два
вызова за сутки удвоили бы лимит — то есть прогрев зависел бы от того, как
отработал крон.

### Дневной сброс и автопауза

`fn_reset_smtp_daily` обнуляет `daily_sent`, катит семидневное окно и ставит
аккаунт на паузу, если доля отказов выше **5%** при **минимум 20 отправках** в
окне.

Порог именно 5%, а не 3%: на прогреве аккаунт шлёт десять писем в сутки, и при
3% два отказа из сорока уже ставили бы его на паузу — а два отказа на холодной
базе это норма. Минимум в 20 писем нужен по той же причине: на выборке из
пяти один отказ весит двадцать процентов сам по себе.

Обе функции вызываются из `daily-report` на тике `0 7 * * *`. Не отдельным
крон-триггером — на бесплатном плане Cloudflare потолок в пять триггеров, и все
заняты. Постоянное место — в блоке «Крон-диспетчер».

Вызываются они из edge-функции, а не из воркера, потому что воркер ходит с
`anon`-ключом, а права на эти функции выданы только `service_role`. Иначе
сбросить счётчики всего пула мог бы любой, у кого есть публичный ключ.

### Выбор аккаунта при отправке

`generate-queue` записывает выбранный аккаунт в `send_queue.smtp_account_id`, а
`process-queue` перед отправкой **перепроверяет** его. Строка может уйти через
сутки после постановки в очередь, и к тому времени аккаунт мог выбрать лимит,
встать на паузу или сгореть; тогда берётся следующий свободный аккаунт того же
бренда.

Если свободного нет — письмо **остаётся в очереди**. Не помечается ошибкой и не
теряется: `markFailed` наращивал бы счётчик попыток и через три прогона выбросил
бы лид насовсем из-за занятого отправителя. В логе это видно как
`no_sender=<число>`.

## Проверить, что аккаунт работает

```sql
-- кого выберет пул для бренда прямо сейчас
SELECT (fn_next_smtp_account((SELECT id FROM brands WHERE slug='1xbet'))).email;

-- состояние пула
SELECT email, status, ramp_stage, daily_sent, daily_limit,
       sent_count_7d, bounce_count_7d, credentials_ref
  FROM smtp_accounts ORDER BY email;
```

Пусто в первом запросе означает одно из четырёх: у бренда нет аккаунтов, все
выбрали дневной лимит, все на паузе, либо у строки не заполнен
`credentials_ref` — последнее функция отсеивает намеренно, чтобы не выбрать
аккаунт, которым физически нечем отправить.

## Тексты писем

Лежат в `email_templates` и правятся без деплоя:

```sql
UPDATE email_templates SET body = '...'
 WHERE brand_id = (SELECT id FROM brands WHERE slug='1xbet')
   AND variant = 'cold_geo' AND attempt_no = 1;
```

Варианты: `cold_geo` (владелец сайта), `cold_youtube`, `cold_appstore`,
`brand_intent` (лиды брендового трафика, есть EN и UZ). У каждого по три темы —
`attempt_no` 1..3.

Плейсхолдеры: `{site}`, `{geo_word}`, `{geo_clause}`, `{keyword}`. Написанный с
опечаткой плейсхолдер уедет в письмо буквально, поэтому миграция проверяет, что
в текстах не встречается ничего, кроме этих четырёх.

**У нового бренда своих шаблонов нет, и чужие не подставляются.** Письма такого
бренда не уходят вовсе, а в `error_log` пишется, какого именно шаблона не
хватает. Это сделано намеренно: подставить текст про 1xBet партнёру LuckyPari —
то же вскрытие связки, что и отправка с чужого адреса.
